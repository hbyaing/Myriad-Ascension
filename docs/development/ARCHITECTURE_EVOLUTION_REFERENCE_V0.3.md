## 1. 这份初版要解决什么

《万界仙途》不是一次性完成的小型模组，而是一个会持续增加玩法、资源、特效、调试能力和附属内容的长期工程。未来还会有多人协作、多个 AI 并行参与、增量更新、旧存档迁移和频繁实验。

因此，架构的目标不是让今天的目录看起来整齐，而是让下面这件事越来越可靠：

> 提出一个新玩法后，开发者或 AI 能迅速找到入口，在局部范围内完成实现，确认它真的生效，并知道它会影响什么。

本初版把两个材料中的结论合并为六个目标：

1. 新增普通内容的成本逐渐降低。
2. 大改一个系统时，影响范围和回归范围可见。
3. 多个系统可以协作，但关键状态只有明确的裁决者。
4. 复杂机制可以使用自己的规则内核，不被万能抽象限制。
5. 请求、计算、实际效果、保存、同步和玩家可观察结果能够追踪。
6. 新开发者和新 AI 不必先读完整仓库才能安全工作。

这不是一次“大重构”方案，而是一个允许持续替换和逐步迁移的目标结构。

本次优化增加了一条执行原则：**领域模块是责任边界，完整功能切片才是实际交付单位。** 任何新结构都必须先在一条真实功能链上证明能减少耦合、提高解释性或降低验证成本，不能只凭目录和接口数量判断成功。

## 2. 当前证据和采用边界

本初版依据以下材料形成：

- 《万界仙途》长期架构：从“模块化工程”升级为“可持续演化的修仙开发平台》；
- 《星期三2113.txt》中的当前工程复核、提交者差异、第一批构建规整和框架讨论；
- 前一轮对 Genesis V7.8.0 框架包的审阅结论；
- 当前仓库已提交的 `ce3c4c5` 构建验证配置拆分及此前源码审计。

材料中有些数字和 CI 结论属于当时记录，不应自动视为今天的运行证明。尤其是 CI #92 的完整最终状态、当前远端分支和生产制品，需要在实际发布前重新核验。

前一轮资源审计给出的量级约为：Java 源码 5 MiB 左右，运行时资源约 145.6 MiB；这说明资源、Shader、模型和贴图账本必须与 Java 包结构并行治理。拆包本身不会自动减少发布包体。

Genesis V7.8.0 可借鉴的部分是“小作者入口 + 明确的状态、执行、失败和清理责任”，尤其适合炼丹、炼器和可验证的跨系统效果。它当前不是《万界仙途》的完整生产 SDK，不能整体复制为强制底层。采用每一项机制前，都要用当前工程的真实入口、存档、网络和 Forge 环境重新验证。

## 3. 总体结构：领域模块化单体

第一初版选择“领域模块化单体 + 可组合能力 + 独立规则内核 + Forge 适配层 + 工程治理层”。最终仍以一个完整 Forge Mod 发布，但内部要能按责任边界独立理解、替换和验证。

```text
内容定义与组合
  法宝 / 功法 / 灵根 / 丹药 / 材料 / Boss / 世界事件
          │ 稳定身份、标签、配置、组合
          ▼
领域规则内核
  炼丹  炼器/法宝  修炼/境界  御剑/战斗  阵法  世界事件
          │ 公开契约：意图、资格、规则结果、失败原因、状态事实
          ▼
运行时执行与状态边界
  权威线程、操作上下文、资源预算、随机源、调度、诊断
          │
          ├── Forge/服务端适配：事件、实体、世界、注册、网络、存档
          ├── 客户端表现：UI、Shader、动画、粒子、音效
          └── 调试与验证：模拟器、数据面板、GameTest、实机证据

横向治理：AI 上下文、变更影响图、资源账本、性能预算、迁移、协作和发布
```

这张图是责任关系，不是要求立刻创建同样数量的 Gradle 子项目。现阶段优先建立逻辑边界和公开入口，再按真实变更压力决定是否拆包。

### 3.1 实际开发单位：垂直功能切片

一个可交付功能应尽量同时包含以下五部分：

1. 内容表达：稳定 ID、配置、资源和兼容版本；
2. 领域规则：可独立测试的计算、资格和失败语义；
3. 运行时操作：权限、线程、资源消耗、重复保护和实际提交；
4. 平台接入：Forge 事件、物品/实体、网络、存档和客户端表现；
5. 证据与诊断：定向测试、调试输出、资源/性能成本和已知限制。

功能切片不等于新建一个包。它是一份能从请求追到玩家可观察结果的责任集合。一个切片允许跨越多个逻辑模块，但必须把跨越的契约和证据写清楚；这样可以防止“目录分开了，运行链仍然互相偷偷调用”。

## 4. 设计原则

### 4.1 内容可以多重归属，状态不能多头写入

一把剑可以同时是装备、法宝、功法载体、炼丹材料和世界事件触发条件。内容分类应允许多重标签和多种用途。

但“具有某种性质”和“有权修改某个状态”必须分开：

- 物品机制负责物品身份、数量和所在位置；
- 法宝领域负责认主、成长和法宝状态；
- 能力或战斗领域负责技能触发与结算；
- 炼丹领域负责它作为材料时的反应解释；
- 存档/同步层负责持久化和向客户端发布权威事实。

多个系统可以读取同一个对象的不同事实，但同一项关键状态要有明确所有者。跨领域改变状态必须经过所有者公开的操作入口，不能直接改对方内部字段。

### 4.1.1 状态所有权矩阵

对试点涉及的关键状态，按需要核对以下分类：

| 状态类别 | 典型内容 | 权威者 | 是否持久化 | 是否同步 | 失败后处理 |
|---|---|---|---|---|---|
| 权威持久状态 | 修为、法宝成长、物品数量 | 对应领域/服务端 | 是 | 按客户端需求 | 走迁移或明确拒绝 |
| 派生状态 | 当前加成、可用资格、汇总值 | 规则计算 | 通常否 | 可按需发送 | 由权威状态重算 |
| 操作中状态 | 炼丹会话、待确认效果 | 执行实例/宿主 | 按操作责任决定 | 不默认同步 | 超时、取消或恢复 |
| 缓存状态 | 查询索引、渲染缓存 | 使用它的子系统 | 否 | 否 | 可丢弃并重建 |
| 表现状态 | UI、动画、粒子阶段 | 客户端 | 否 | 接收事实 | 随新事实重建 |

状态表不是登记负担，而是解决三个实际问题：谁能写、退出后是否还存在、客户端看到的是否是权威事实。没有这三个答案的状态，不应被新的跨系统功能继续依赖。

对关键字段和操作进一步区分三个责任：业务裁决者、实际存储/保管者、允许写入的入口。例如法宝领域裁决成长规则，ItemStack NBT 携带成长数据，背包、容器或炼器任务保管当前物品；转移和恢复必须由相应入口保持身份与数量一致。共享存储不意味着其中全部字段属于同一个领域；规则、存储和同步也无需集中在同一个类。

只为本次改动涉及的权威状态补充：字段或记录、写入口、保管位置、保存/恢复路径和必要同步。表中“操作中状态”是否必须持久化，要根据退出后仍承担的责任判断；不能把已消耗资源的未决操作简单当作可丢弃缓存。

### 4.2 领域内部完整，跨领域接口小而明确

炼丹、炼器、渡劫、御剑和世界事件的内部规则不同，不应为了整齐而强行变成同一种“组件 + 数值加成”。

领域内部可以有自己的模型、规则和测试；对外只公开必要的稳定语义，例如“提交材料”“检查资格”“查询进度”“领取结果”“确认实际伤害”。

公共底层只承载真正稳定且反复出现的能力：身份、版本、资源访问、随机源、时间/调度、操作上下文、诊断、存档迁移基础和网络传输基础。它不裁决“炼丹成功”或“渡劫成功”这种领域含义。

### 4.2.1 依赖方向和禁止依赖

以下表示候选编译依赖；运行数据流、调用顺序另按具体操作描述：

```text
领域规则 → 领域数据模型与必要的基础契约
内容定义/加载器 → 对应领域的公开数据模式
Forge 适配器 → 领域公开入口及领域声明的平台端口
客户端表现 → 网络数据结构和客户端表现接口
调试工具 → 被测公开入口、只读诊断接口
组合根 → 领域实现与适配实现，负责接线
```

领域规则不得反向抓取 Forge 全局对象；客户端不得自行宣布服务端结果；调试器不得绕过公开入口后把夹具结果当作端到端证据；领域之间不得直接写入彼此的内部状态。临时违反时必须记录兼容原因和移除条件，否则它会变成新的公共依赖。

需要世界能力时，由领域声明最小端口、平台侧实现；公共契约不引用具体领域实现或 Forge。现有类与包名尚未遵守全部候选边界，不能直接把图转成全仓检查。先对试点目录建立禁止引用检查，保留已有例外及复核条件。静态检查能识别引用关系，无法独自证明状态写入合法或业务含义一致，仍需接口约束和行为验证。

### 4.3 用可信操作连接完整运行链

复杂功能不以“某个函数被调用”作为完成标准，而以完整链路作为验收边界：

```text
触发/请求
  → 资格与条件
  → 规则计算
  → 形成执行计划
  → 在权威边界提交实际状态
  → 保存与同步
  → 观察实际结果
```

对需要跨系统或外部效果的操作，应能区分：请求已收到、计划已生成、效果已发出、效果已确认、未执行、状态未知。是否需要取消、重试、补偿、重复保护和未决记录，按该操作的实际责任决定，不预先制造一个包办一切的全局事务管理器。

可以借鉴 Genesis 中的身份分层：请求意图、执行实例、不可变计划、效果实例分别拥有稳定标识。但只有在真实需求涉及重试、迟到回执或跨边界效果时才引入对应层次。

### 4.3.1 重要操作的最小契约

针对持久化、高价值或跨领域操作，按实际风险记录：输入与权限、操作身份及重试范围、提交点、后续义务、可观察结果、失败后允许采取的下一步。

结果至少要区分下面几个维度，不预设一个统一枚举覆盖全部语义：

| 维度 | 应回答的问题 |
|---|---|
| 权威变更 | 没有修改、已经提交，还是目前无法确认？ |
| 当前阶段 | 等待执行、正在执行、等待外部确认，还是已经结束？ |
| 后续义务 | 还需交付、保存、同步、补偿或人工核对什么？ |
| 重试方式 | 可重新提交、只能查询原操作、仅重发通知，还是必须先恢复？ |

“已提交但同步失败”同时包含提交成功与后续失败，不能用单个 FAILED 引导调用者重新扣料。网络重复请求、重复执行和重复展示要分别处理。无权威修改的拒绝应有稳定原因；未知结果应保留原身份并走查询/恢复入口，不能直接再发奖励。

精确重试需要明确身份、有效期、跨重登/重启范围。同一炉忙碌时拒绝第二次开炉，仅证明占用保护，不等于任何时刻重放旧请求都返回原结果。单文件原子替换也不等于批次、区块和玩家数据整体原子提交。

流程图用于追踪责任；具体操作允许不同阶段顺序。哪些步骤可部分完成、失败后谁收尾，由该领域与真实平台条件决定。

### 4.4 规则、状态和表现分开

- 能脱离 Minecraft 的计算，尽量放入可单独运行的规则内核。
- 服务端拥有权威状态、资格判断和实际结算。
- 客户端接收必要的权威事实，负责交互、UI、动画和视觉表现。
- 存档状态、网络状态、临时缓存、调试覆盖要明确区分。
- 涉及实体碰撞、区块生命周期、真实渲染和玩家感知的行为，必须保留 Forge/实机验证入口。

编译通过只能证明代码可编译；规则测试只能证明规则模型；GameTest 只能证明其覆盖的游戏路径。生产发布和玩家实际感知需要另外的证据。

### 4.5 复杂能力允许独立内核

普通被动加成、触发条件、消耗和目标筛选可以组合已有能力。自由炼丹反应、空间折叠、时间操作、复杂灵根演化等机制，如果强行塞入统一配置或万能效果列表，会变成另一套难以调试的语言。

架构应同时允许：

- 数据定义：新增草药、丹药、材料和基础数值；
- 组合配置：用已有条件、消耗、目标和效果组成新内容；
- 代码扩展：通过领域正式入口加入新规则内核。

这三类入口要有不同的验证和兼容要求。

## 5. 逻辑模块与责任边界

下面是目标逻辑地图。它是导航和责任划分，不要求立即移动现有类。

| 逻辑层 | 主要内容 | 应负责什么 | 不应负责什么 |
|---|---|---|---|
| `content` | 物品、材料、丹方、功法、法宝、灵根、Boss 定义 | 稳定 ID、标签、配置和内容组合 | 直接改玩家/世界权威状态 |
| `kernel` | 身份、版本、随机、调度、操作上下文、诊断 | 反复出现的基础语义和安全边界 | 具体修仙玩法结论 |
| `domain.alchemy` | 炼丹模拟、药性、控火、配方、出丹 | 炼丹规则、结算计划、炼丹记录 | Forge 注册、UI 绘制、玩家数据所有权 |
| `domain.artifact` | 法宝认主、成长、词条、装备效果 | 法宝状态与法宝规则 | 任意改写背包或其他领域状态 |
| `domain.cultivation` | 修为、境界、功法、灵根相关读取/发展 | 修炼状态与规则入口 | 直接替代物品、网络、渲染层 |
| `domain.combat/yujian` | 目标资格、命中、伤害语义、御剑 | 战斗/御剑规则和结果 | 自行决定所有物品和存档细节 |
| `domain.world` | 世界事件、区域、渡劫等 | 世界生命周期和事件规则 | 依赖客户端表现完成权威结算 |
| `runtime` | 执行上下文、权威线程、预算、生命周期 | 组织一次可信操作并返回结果 | 解释具体领域规则 |
| `forge.server` | 事件、实体、世界、注册、存档 | 将 Forge 事实适配给领域和运行时 | 把完整业务逻辑堆在事件监听器 |
| `forge.network` | 消息编解码、同步协议 | 传输版本化事实和请求 | 作为第二套业务规则 |
| `client` | UI、Shader、动画、粒子、音效 | 表现和客户端交互 | 伪造服务端权威结果 |
| `tools` | 模拟器、调试面板、GameTest、诊断 | 快速研究、复现和证据生成 | 绕过真实入口后宣称端到端通过 |

组合根负责注册、装配和依赖接线。领域模块不能反向抓取 Forge 全局入口；平台适配负责把真实环境事实转换为领域契约。

## 6. 面向作者和 AI 的三类扩展入口

### 6.1 内容定义入口

适用于常规新增内容。作者只提供稳定 ID、标签、参数、资源引用和兼容版本。系统负责校验 ID 冲突、字段范围、资源存在性和版本迁移。

例如，新增普通丹药不应要求修改中央玩家数据类、网络大包和全局事件入口。

### 6.2 能力组合入口

适用于用已有机制组合新玩法。组合对象按能力需要表达触发条件、资格条件、消耗、目标、效果和失败原因；涉及依赖和冲突时先明确阶段，再决定顺序。数字优先级不能让尚未确认的结果提前成为事实。诊断记录按排错和恢复需要保留，避免让每个普通效果承担完整持久事务成本。

“法宝同时参与战斗、成长和炼丹”应通过各领域的公开入口连接，而不是让一个全局组件替它们共同持有所有状态。

### 6.3 领域规则扩展入口

适用于无法用现有组合表达的新机制。扩展者需要声明：输入事实、输出结果、状态所有者、线程要求、持久化要求、网络影响、资源/性能预算、失败语义和验证入口。

复杂规则可以拥有独立内核，但必须通过正式适配层接入 Minecraft；不能直接从任意事件监听器写入多个领域的内部状态。

## 7. AI 工程化：把上下文和证据做成工程资产

长篇规范不能代替可检查边界。每个重要领域应有一份机器可读或结构稳定的工程契约，至少包含：

| 字段 | 含义 |
|---|---|
| 规则所有者 | 哪个领域拥有最终裁决权 |
| 输入事实 | 允许读取哪些数据、来自哪里 |
| 输出结果 | 返回什么计划、结果或失败原因 |
| 状态权威 | 服务端、世界、玩家、物品或临时会话 |
| 扩展入口 | 数据、组合或代码扩展位置 |
| 禁止事项 | 不得直接调用/修改的对象 |
| 生命周期 | 加载、运行、重载、退出、恢复要求 |
| 验证命令 | 最小可复现测试和实机入口 |
| 资源/性能预算 | JAR、资源、Tick、网络、渲染等成本 |
| 证据 | 提交号、日志、测试名、已知限制 |

每个 AI 任务还应形成一个小任务包：目标、范围、源代码地图、必须保留的行为、潜在影响、允许修改的文件、验证命令、结果摘要和未覆盖部分。

任务包应能被下一名开发者或 AI 独立使用，最小格式建议固定为：

```text
目标：要改变的玩家可观察行为
基线：当前提交号、版本、已知旧行为
入口：触发点、规则入口、状态所有者、保存/同步路径
范围：允许修改的目录/文件与禁止越界的区域
不变项：旧存档、网络协议、失败语义或用户工作方式
验证：规则测试、GameTest、客户端实机、发布检查
证据：命令、日志、截图/录屏位置、提交号
限制：没有证明的部分、待补测风险
```

这比要求 AI 先阅读整个仓库更可靠，也比只给一个类名更安全。任务包中的“证据”必须对应最终提交，历史截图或另一版本的测试不能自动继承为当前保证。

`AI_SOURCE_MAP` 继续保留，但要逐步绑定提交号、核查日期、责任者和测试入口；它是导航，不是源码的替代品。能自动生成的索引应从代码或构建配置生成，避免文档长期漂移。

多人和多 AI 并行时，优先分配领域内部完整的任务；共享入口变更应单独成任务并先审查。通过变更影响图提前显示会触及哪些中央文件、存档、网络协议、资源和测试。

任务包还应按需声明受影响的规则、状态字段、协议、资源定义以及消费者。例如一项任务修改灵根倍率，另一项修改法宝如何读取倍率，即使文件完全不同，也可能产生语义冲突。影响清单帮助集成者定位相关任务；静态引用无法全面发现语义冲突，合并后的关键行为仍需联合验证。

源码路径、注册入口和验证命令可以逐步自动校验或生成；状态权威与规则含义由负责该领域的人或 AI 审核。先补高价值入口，避免为每个普通内容生成全套登记。生命周期声明按具体服务记录创建、允许调用的阶段、热重载策略、玩家/区块离开后的义务和服务端停止清理；持久记录与可丢弃缓存分开处理。

## 8. 调试、解释和验证

“有数值结果”不等于“功能生效”。每个重要操作应尽量能够解释：

```text
检测到触发
→ 已装备法宝
→ 境界条件满足
→ 灵力足够
→ 目标关系检查通过/拒绝
→ 规则计算得到计划
→ 服务端实际提交
→ 生命/物品/世界状态发生变化
→ 保存并同步
```

调试覆盖应区分三种作用：

1. 只读观察：查看当前状态、规则选择和失败原因。
2. 临时实验：只在当前测试会话覆盖输入或参数，不写正式存档。
3. 正式修改：经过明确授权后修改持久化数据，并记录迁移/审计信息。

验证分层：

- 纯规则测试：验证计算和边界条件；
- Java/契约测试：验证 API、失败语义和编译边界；
- Forge/GameTest：验证真实服务端入口、存档和事件链；
- 客户端实机：验证渲染、交互、HUD、网络和玩家可感知结果；
- 发布检查：验证生产 JAR、资源、Shader、性能和迁移。

正常成功与必要反例都要保留。不能让夹具绕过真实入口，也不能因为所有请求都被拒绝而得到“测试通过”。

## 9. 资源、性能和包体治理

资源治理与代码模块化并行进行。对每次新增内容登记实际成本：

- 生产 JAR 与运行时资源体积；
- 贴图、模型、网格、Shader、音效分类体积；
- 加载时间和内存峰值；
- 服务端 Tick、区块/世界采样、网络同步；
- 客户端渲染、粒子、动画和全屏效果。

先建立账本和基线，再决定压缩、延迟加载、资源合并或删除。不能以“拆成更多包”推断包体会减少，也不能为了压缩牺牲已经确认需要的视觉质量。

材料记录的 CI #92 曾出现“构建与 GameTest 前置项通过，但警告预算 120/119 导致工作流失败”的情况。该记录说明发布门槛必须细分：构建、测试、警告预算、生产 JAR 上传和实机证据不能合并成一个模糊的“成功”。当前最终结果仍需重新运行确认。

飞行优化曾受到植物/生物群系采样影响，说明性能责任不能只放在单个玩法里。跨系统采样需要声明阻塞方式、缓存、失效条件、线程和每 Tick 预算。

## 10. 渐进实施路线

### P0：固定当前基线

保存可构建提交、Java/Forge/Gradle 版本、验证命令、警告预算和当前 CI 结论。重新核对远端主分支和生产制品，不把历史记录当成当前保证。

### P0.5：建立生产制品和资源账本

记录 JAR、贴图、模型、Shader、音效和加载成本。将大体积截图、日志和个人绝对路径文件移出源码交付路径，保留可复现摘要和必要索引。

### P1：建立最小系统地图和状态所有权表

先不移动大量类，记录关键入口、读写者、存档/同步路径和领域责任。优先处理 `CultivationDataImpl`、中央注册/网络入口、炼丹模拟、法宝效果与御剑目标判定等真实热点。

### P2：核实已有切片，再选择接口与跨领域试点

在 `7c85083` 中，炼丹已经有完整 V5 链路：AlchemyService 接入 startV5Batch，V5Batch 准备规则和输入快照，BatchJournal 保存批次与位置关联，方块实体恢复并推进批次，BatchDelivery 负责领取及回执恢复。旧 CraftingJobs 同时保留旧炼丹与炼器任务。不能另建与这些记录竞争的制造权威。

候选试点一：补齐 V5 导航、状态和提交边界，选择一个开炉入口，将难解释的 boolean 收敛为明确的领域结果，保持既有日志格式、领取协议和玩法。候选试点二：审查法宝—御剑的目标资格差异，形成目标矩阵后决定共享哪些事实。按实际开发需求、干扰范围和验证成本选先后，不将两者绑定为硬前置。

炼丹试点需核对的行为包括：

- 在已声明的操作身份和重试范围内，不重复扣料或领取；
- 材料不足、配方不存在和资格不满足都有稳定失败原因；
- 规则结果与实际物品/玩家状态一致；
- 退出、重登和资源重载不会静默丢失或污染结果；
- 客户端显示来自服务端事实；
- 调试器能给出从输入到结果的解释链。

已有 V5BatchGameTests 定义了托管锁定、旧区块恢复、满背包、重复领取和交付恢复等测试。本版只读取测试定义，没有复跑；手动构造旧状态不能代替进程强退与真实故障注入。

法宝目标判定实际复用御剑 canTarget 后追加排除条件，御剑条件包含视线。共同的目标事实可复用，最终裁决由能力决定；穿墙法宝不应无意继承御剑视线限制。当前行为是否需要改变，仍需具体玩法要求。

另一个独立调查点是炼器启动中的扣料、扣灵力、炉体更新和 CraftingJobs 登记，以及 BatchJournal.write 中批次写入与认证/研究副作用的衔接。存在多步提交边界不等于已经发现数据丢失，需先核对异常和恢复语义。

开炉同步保存区块、日志 force(true)、领取保存/读取玩家数据是实际存在的 I/O。先测代表性负载，再决定优化；异步化必须保留持久化保证。

### P3：引入小作者入口

在试点成功后，为炼丹、炼器或法宝效果提供小而明确的意图/结果 API。作者不直接管理库存和权威状态；宿主负责资格、扣费、重复保护、结果发布和生命周期。

### P4：建立 AI 任务契约和自动索引

将入口地图、领域契约、变更影响图、验证命令和证据摘要纳入工程。自动检查资源缺失、重复注册、网络 ID 冲突、客户端代码误入服务端和未登记的资源/性能成本。

### P5：按需求迁移和清理旧实现

只迁移已经通过试点证明边界收益的领域。保留兼容门面和旧存档迁移路径，逐步删除重复逻辑。每次删除都必须有行为证据和可回退提交。

## 11. 第一版验收场景

这套架构是否有效，先用需求压力测试，而不是用类数量评价：

| 场景 | 第一版应看到的结果 |
|---|---|
| 新增一种普通丹药 | 主要修改内容定义、资源和炼丹领域的必要入口 |
| 新增独特炼丹反应 | 主要修改炼丹规则内核，不改大量 Forge 交互代码 |
| 法宝同时参与战斗、成长、炼丹 | 每个领域解释自己的用途，物品身份和状态仍有唯一所有者 |
| 大改某种灵根效果 | 能列出消费者、存档/同步影响和对应验证入口 |
| 修改法宝目标规则 | 能区分目标拒绝、效果未发出和效果已发出但未确认 |
| 玩家断线、重登、换维度 | 关键状态可恢复，结算不会重复或静默丢失 |
| 新 AI 接手故障 | 仅依据入口地图、契约和复现命令即可定位到有效范围 |
| 两名开发者并行加玩法 | 主要在领域内部修改，共享契约变化可单独审查 |
| 新增大型 Shader | 有资源和性能登记，并能通过真实客户端入口验证 |

建议持续记录四类趋势：共享热点文件数量、一次需求修改的跨领域文件数、故障定位所需时间、每次新增内容的资源/性能成本。先记录基线，再决定目标值，不虚构未测出的收益。

选一个代表性跨领域变化验证扩展性，如法宝新增特殊目标条件；领域内测试成功不能单独证明跨领域组合正确。比较直接沿用、领域内封装和公共抽象三个方案时，保持相同旧行为、失败恢复、平台与验证要求。只有共同语义、生命周期和失败策略稳定时才考虑共享；某些独立接口也可因明确的替换需求而提前建立，不机械要求先有两份重复代码。

每个新增公共抽象记录：解决的真实问题、采用代价、预期收益、验证任务和撤销条件。用第二个实际需求检查改动范围；收益未成立时允许保留局部实现。无需为比较而维护三个完整生产版本。

## 12. 当前不做的事

- 不立即把整个仓库拆成多个独立 Mod 或微服务。
- 不把所有玩法统一成一个万能效果/事务/组件框架。
- 不为了目录整齐而一次性移动 `CultivationDataImpl`、网络大包和中央注册体系。
- 不把 Genesis V7.8.0 当作已经适配当前 Forge 版本的生产 SDK。
- 不把纯 Java、GameTest 或历史截图证据直接等同于客户端实机和多人存档保证。
- 不在灵根设计尚未稳定的情况下提前冻结所有灵根终点；本架构只提供其接入和演化边界。

## 13. 第一版结论

《万界仙途》的长期架构应当是一套“领域内部完整、跨系统契约明确、内容能够组合、复杂机制有独立内核、运行结果可解释、修改能够验证”的模块化单体。

它的核心不是预先设计出所有模块，而是建立一种可持续的工作方式：每个系统知道自己拥有的状态，每个跨系统操作都有清楚的入口和结果，每个 AI 任务都有最小上下文与证据，每次新增内容都能看见自己的资源和性能成本。

第一步不应是大规模搬迁代码，而是用一个真实的跨系统试点把这条链跑通。试点成功后，架构才有资格向更多领域扩展；试点失败时，也能在小范围内修正边界，而不会把整个模组一起锁死。
