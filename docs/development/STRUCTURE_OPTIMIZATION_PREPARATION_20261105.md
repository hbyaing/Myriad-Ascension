## 2. V5 炼丹实际链路

Java 根目录：`src/main/java/cn/blockforge/generated/generatedmod/`。

| 阶段 | 入口 | 当前责任 |
|---|---|---|
| 网络准入 | `network/service/AlchemyService.handleAlchemyPacket` | 玩家、距离、菜单、结构、占用及新旧任务检查 |
| 开炉 | `AlchemyFurnaceBlockEntity.startV5Batch` | 资格、配方材料分配、准备批次、写日志/关联、发布炉状态和保存区块 |
| 规则准备与过程 | `alchemy/batch/V5Batch` | 批次 ID、输入/规则快照、燃料与材料托管、过程推进及成品准备 |
| 独立规则 | `alchemy/simulation/AlchemySimulation` | Snapshot、Operation、Ledger、确定性采样与预算校验；不直接发物品 |
| 持久记录 | `alchemy/batch/BatchJournal` | 批次、位置、待交付索引；写入同时关联认证和研究记录 |
| 恢复/发布 | 方块实体 `restoreV5`、`tickV5` | 由日志恢复炉状态，写新记录后应用；异常隔离并保留恢复资料 |
| 领取 | `alchemy/batch/BatchDelivery.claim` | READY → DELIVERING → CLAIMED；库存回执、玩家保存及读取检查 |
| 交付恢复 | `BatchDelivery.login`、`tick`、`recover` | 登录及周期处理未完成交付 |
| 旧路径兼容 | `network/service/CraftingJobs`、`AlchemyService.tickAlchemy` | 旧炼丹、炼器任务、到期索引和退款；不可当作无用旧代码直接删除 |

现有 tests：`src/gametest/java/cn/blockforge/generated/generatedmod/V5BatchGameTests.java`。已定义拒绝不变更、托管锁定、旧区块恢复、满背包、重复领取、交付恢复、拆炉和实际 tick 完成；本轮只核对定义。

## 3. 先保留的责任边界

- 批次文件与区块、玩家数据是不同存储，不能因单文件原子替换就声明整体原子性。
- V5 批次快照是恢复依据，方块实体同时承担平台对象和视图；移出方法不能另建竞争权威。
- 领取检查的是带批次身份的真实库存回执，不是一次普通 addItem 调用。
- 玩家灵力仍由现有玩家数据负责；炉内预存燃料和批次托管按已有机制处理，不能重复扣费。
- 旧任务与 V5 同时参与忙碌检查，兼容路径须先追踪调用者再迁移。

## 4. 首批改造任务与验收

### A：源码导航修正（本次完成）

在 AI_SOURCE_MAP 中补充 V5 权威/恢复入口，修正验证任务定义位置。验收是链接和符号在基线树中存在、说明符合源码；不需要为了文档修改运行完整游戏测试。

### B：开炉资格与失败结果（候选首个 Java 改造）

先枚举 startV5Batch 及网络入口的真实拒绝分支、提示和调用者，再引入领域内最小结果结构。保留 boolean 兼容入口或同步适配全部调用者，以消费者数量和语义为依据。不得把“写入发生后抛异常”误报为“未提交”，也不在同一提交重写 BatchJournal 或 BatchDelivery。

验收：既有正常开炉、资格拒绝、托管、恢复与领取行为保持；拒绝原因能够被实际菜单/请求调用者正确处理；未提交的拒绝不改库存、燃料或玩家状态。保存确认失败与普通资格拒绝需可区分。完成 Java 改造前运行相关 GameTests、构建检查，按实际 UI/协议影响补充集成验证。

### C：法宝—御剑目标矩阵（可独立推进）

`artifacts/ArtifactEffects.target` 复用 `yujian/YujianController.canTarget` 并追加 spectator、侍从、OwnableEntity 和盔甲架排除；御剑条件还涉及视线、盟友和 PvP。先列出本人、友方、他人宠物、盔甲架、遮挡和玩家目标的预期，不因代码相似统一裁决。当前未知玩法需求以现有行为为回归基线。

验收：现有两个入口的行为矩阵明确，共同事实与能力裁决有据可分。新增穿墙等规则须有实际玩法授权，不由结构优化自行改变。

### D：持久化边界与 I/O 测量（调查任务）

BatchJournal.write 包含认证 reserve、批次文件写入、认证 record、研究 record 和缓存维护；需逐一核对异常后的可重入与恢复。开炉 save(true)、日志 force(true) 与领取保存/读取 player.dat 的耗时需实测。先记录单炉/多炉/领取/恢复负载及 tick 数据，再决定是否调整同步机制。

验收：能解释每个提交点之后失败时谁负责结清；有测量输入、环境和结果，才提出性能收益。异步化与删保存步骤不能作为默认优化。

## 5. 开始 Java 改造前的运行准备

1. 固定最新主线和干净工作区，检查实际 AGENTS 约定和用户并发改动。
2. 补齐构建所需源码、资源与依赖，使用实际 Java 17；明确稀疏检出和缺失输入。
3. 保存未修改版本的相关验证基线，再改代码。原有失败单独记录，不靠放宽预算消失。
4. 当前 `-PentryUiOnly` 选择 `wuxingxiantu_entry` 命名空间，V5BatchGameTests 也归入它；它不是只运行一个批次类。先核对任务图和测试发现范围，再声称定向测试覆盖。
5. UI、存档、网络或运行性能发生变化时，分别补足对应验证；所有结果绑定最终提交。
