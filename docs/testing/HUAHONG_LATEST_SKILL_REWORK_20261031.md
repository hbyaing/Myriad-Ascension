## 实机对照标准

每族在相同路径、视角、背景、曝光和完整强度下观察，分别保存侧视、斜角、追尾、近距与停飞序列；普通路径及实例实际使用的光影路径均要验证。先核对外轮廓、负形、主体与尾迹比例，再看材质流向、层次和退出。

- 虹核：饱满头与前柔光连续，没有新生独立球头、尖端黑缝、瞬间收细或前后倒折；不能把减亮或删团当作连续性修复。
- 燃尾与赤焰：看主舌的曲率、不同长度、宽红外焰与暗缝、根部层次、脱落后保留的世界残焰；避免等宽线刷、放射花或整段矩形切口。
- 长虹：核有集中长梭的长度和柔光，世界主长迹保持单束；伴流是弱层，不能全体等亮，也不能把主躯删成像素细线。
- 羽膜与扇纱：斜角和追尾仍能看出不同空间层及真实弧面；宽膜、细筋与稀疏枝条有层级，不呈实体翼板、平面梳齿或只换色的共同锥尾。
- 烟：明暗背景中仍有近黑吸收、细碎气态边、局部红裂光与团间空隙；旧烟不绕当前载体转动，不把静态图集变体宣称连续流体模拟。
- 蓝白虹流：检查真正穿过三维场的视差、厚度、遮挡和同场虹筋；独立原创适配与参考源码逐像素还原是不同结论，必须分别说明。
- 抽搐：不仅检查中心线，还要记录真实网格顶点或各截面侧向偏移、同一段世界历史、完整掉头、tick 交界、正轴视角和实体 tick 增长。静止夹具、只看挂点为零或只检查帧数不足以通过。

## 真实服务端漏调度复现与修复

`native-diagnostic2` 的服务端记录暴露了实际模拟漏 tick，而不是路径测试时钟误差：测试阶段 230 / 232 / 234 已连续发送 `forward=false`，世界 tick 为 252 / 254 / 256，但载具 `tickCount` 始终 158、乘客始终 171，位置、朝向和化虹 stage=2 均冻结。阶段 236 才继续推进。故不能靠延长停飞或掉头阶段、改用乘客 tick 作为测试时钟掩盖冻结。

本轮直接检查了实际使用的 Forge 1.20.1 / 47.4.10 映射 JAR 中的调度实现，确认两道独立门：

1. `PersistentEntitySectionManager.getEffectiveStatus()` 使用实体 `isAlwaysTicking()` 决定其有效 section 状态；`Callback.onMove()` 与区块状态更新据此开始或停止 ticking。
2. `ServerLevel` 的实体循环另行检查 `DistanceManager.inEntityTickingRange()`。仅覆盖实体的 `isAlwaysTicking()` 不会绕过这道门。

`ServerLevel.tickNonPassenger()` 在载具完成后递归执行 `tickPassenger()`；玩家乘客不会在另一路径独立补齐该实体 tick，所以载具被漏调度会同时冻结乘客的实体 tick。

修复范围仅限活着的主人实际骑乘的 `ControlledSwordEntity.flightRoot`：

- 保留原客户端本地乘客例外，并给合法服务端 owner rider 同样的 section ticking 例外；普通攻击剑、无人 root、错误主人和其他实体不获得该权限。
- 生产实体 `tick()` 记录当前 level `gameTime`。`FlightRootTicking` 在服务器 `LevelTickEvent.END` 只遍历该 level 玩家，补执行本世界 tick 尚未执行、已加入世界且可更新的合法载具。
- 补调度使用原版公开的 `guardEntityTick(level::tickNonPassenger, root)`，同时推进载具和真实乘客；正常路径已经执行的载具跳过，同一个世界 tick 重入也不重复执行。
- 继续调用原来的权限、生命周期、输入、资源消耗和 `FlightCollision.sweep`；没有增加区块 ticket 或同步地形读取，未就绪地形仍应刹停，补 tick 不等于授予穿过未加载地形的权限。

新增 `FlightRootSchedulingGameTests` 对真实 manager 有效状态及真实 `ServerLevel` tick 入口进行验证；以下四项均已包含在上述 493 项必需测试通过结果内：

| 调度用例 | 实际验证 |
| --- | --- |
| `skippedCarrierGetsOneRealTickAndItsPassenger` | 从真实 `EntityTickList` 移除合法载具后，补入口让载具和乘客的实体 tick 各加一；同一 `gameTime` 再调用不加；加载区块计数不变；实际 manager 对 TRACKED / HIDDEN section 的有效状态为 TICKING |
| `normallyScheduledCarrierIsNeverSupplementedAgain` | 先经原版 `guardEntityTick(tickNonPassenger)` 正常执行，随后 END 补入口不再推进载具或乘客 |
| `supplementExcludesWrongOwnerOrdinaryAndUnriddenSwords` | 错误主人、普通剑与无人 root 不获补 tick 或 always-ticking 权限；普通剑实际 manager 状态仍为 TRACKED |
| `supplementalMovementStillWaitsAtQueuedTerrain` | 补入口真实执行载具模拟，pending 地形仍保持 `getChunkNow == null`；真实 sweep 不越过未就绪边界，不将加载等待判为撞墙，也不强制同步完成地形加载 |

客户端动态仍需用原掉头/停飞阶段复跑并观察，不以这四项服务端用例替代画面验收。

## 客户端播放时钟倍率修复与最终复验

客户端实体与服务端世界不一定以相同 tick 速率推进。旧 `FlightInterpolation` 将每个客户端 tick 直接当作一个服务端 tick；服务端降为客户端的二分之一、三分之一或四分之一速率时，三 tick 缓冲会反复耗尽，呈现一次推进完整服务端位移、随后停住数帧的锯齿。提高传送距离阈值不能修复这类时钟倍率错误。

本轮根据最近 16 次不同客户端 tick 的有效到包观察估计 `serverTick / clientTick` 斜率。同一客户端 tick 的批包合并为一次观察，短暂重蓄不清空时钟窗口，滤除一次独立延迟与追包造成的两端离群间隔。斜率上限为 1；正常 20 Hz 播放不会因服务器追赶批包而变成四倍速，缓冲纠偏仍只允许相对估计速率上下 20%，所以正常时钟的追赶上限为 1.2。真实数据耗尽时仍停止在最新已验证快照，不向未收到的未来位置外推。旧序、同 tick 重复或更正包继续忽略；超过 20 个服务端 tick 的断段，以及相邻 tick 的真实位置跳变，保持原有语义。没有修改 `INPUT_TIMEOUT`、传送阈值、服务端速度、碰撞或地形加载权限。

正常到包保持三个服务端 tick 的低延迟；批量到包按已观测的批包跨度增加目标播放缓冲延迟，目标上限为 **16 个服务端 tick**，仍使用原有最多 32 个快照的容量。正常 20 Hz 下这个目标上限约 0.8 秒，半速服务端约 1.6 秒，四分之一速约 3.2 秒；实际网络停顿与排队可再增加端到端延迟。这是有界的缓冲目标与连续播放取舍。恢复连续到包后目标延迟平滑回落到 3 tick，增加延迟只通过减速或安全重蓄建立余量，不倒播。超过这个观察预算的真正停包仍安全保持，不能把这种必要保持计为可消除的抖动。

实际 `native-final` 证明早期自适应版本仍有批包缺陷：羽流整个 552 个客户端 tick 只推进 246 个服务端 tick，估计倍率却始终为 3.515～3.699；第 5243、5244 帧各仅推进一个客户端实体 tick，真实位置分别跳了 52.97、56.38 格，之后第 5249～5255 帧在服务端仍有前进速度时反复等待。限制倍率、保留跨批包观察与自适应延迟共同修复这一类前进过快后耗尽的循环；只把上限从 4 改成 1，仍不能让过短的缓冲覆盖较长批包间隔。
